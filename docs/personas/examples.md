# 캐릭터 질문–답변 예시 (few-shot)

묘묘와 무진의 성격이 설명만으로는 실제 풀이에 충분히 드러나지 않아, 캐릭터별로 질문–답변 예시를 관리하고 그중 작성 용도에 맞는 것을 골라 **실제 생성 요청**에 넣는다. 이 문서는 사람이 읽는 설명이고, 원본은 코드다.

| 무엇 | 코드 |
| --- | --- |
| 타입 (예시 하나의 칸) | `src/domain/personas/examples/types.ts` |
| 묘묘 카탈로그 `myomyo-examples-1.0.0` | `src/domain/personas/examples/myomyo.ts` (참고 문답 원문은 `myomyo-references.ts`) |
| 무진 카탈로그 `mujin-examples-1.0.0` | `src/domain/personas/examples/mujin.ts` (원문 21개는 `mujin-originals.ts`) |
| 선택 정책 `example-select-1.0.0` | `src/domain/personas/examples/select.ts` |
| 지시에 붙이기 (경계 안내 포함, 한 곳) | `src/server/llm/example-block.ts` |
| 결과의 예시 문장 겹침 표 (평가용) | `src/domain/personas/examples/echo.ts` |

## 1. 정책 (2026-11-13)

> 캐릭터별로 관리하는 질문–답변 예시 중, 현재 작성 용도에 맞는 예시를 선별하여 실제 LLM 생성에 사용한다.

이전 정책("예시 문답은 기본 생성 입력에서 제외한다, 개발·평가 자료로만 쓴다, 런타임 examples를 비워 둔다")을 바꿨다. 이전 정책은 묘묘 1.x에서 '판단 → 밋밋한 말 → 묘묘의 말' 예시가 같은 판단의 주제에 문장째 옮겨진 일 때문이었다 (`docs/READING_QUALITY.md` 22절). 이번에는 다음으로 그 위험을 줄인다.

- 예시마다 그 예시에만 해당하는 전제(사용자 사실, 예시용 판단·조건·한계)를 붙여, '이 판단이면 이 문장'으로 읽히지 않게 한다.
- 예시는 지시 맨 끝의 `[캐릭터 문답 예시]` 블록에만 넣고, 현재 사용자의 작성 재료(사용자 메시지의 JSON)와 메시지 자체를 나눈다. 예시를 사용자와 캐릭터의 이전 대화(user/assistant 메시지)처럼 넣지 않는다.
- 경계 안내는 블록 맨 앞 한 곳에만 둔다 (아래 5절).
- 매 요청에 전부 넣지 않고 2~3개만 고른다. 같은 풀이의 재시도는 같은 예시를 받는다.

다른 규칙은 그대로다: 실제 OpenAI 호출 제한, 환경 파일 접근 제한, 엔진과 앱의 책임, 근거 보존, 사용자 개인정보 보호. 캐릭터 설정(`MYOMYO` 2.1.0, `MUJIN` 1.0.0)도 바꾸지 않았다. 예시는 성격을 전달하는 보조 수단이다.

## 2. 예시 하나의 칸

| 칸 | 뜻 |
| --- | --- |
| `id` | 고유 ID (`myomyo-b-02`, `mujin-05`, `mujin-rw-09`). 캐릭터·세트가 달라도 겹치지 않는다 |
| `personaId`, `version`, `setId` | 캐릭터, 예시 하나의 버전, 세트 (묘묘 A/B/C, 무진 original, 재작성 rewrite) |
| `routes` | 쓸 수 있는 생성 경로: `reading`(묘묘 최초 풀이), `followup`(후속 답변), `voice`(무진 Pass 2). 비어 있으면 어떤 요청에도 넣지 않는다 |
| `topics`, `purposes`, `length` | 주제, 표현 목적(첫 안내, 강점, 약점, 설명, 비교, 상황 적용, 확정 불가, 진지함, 칭찬, 도발, 의심, 오류 정정, 한계, 재방문, 캐릭터 잡담), 길이(short·medium·long) |
| `serious`, `reaction`, `needs` | 진지한 상황 예시인지, 반응 예시(칭찬·도발·의심)인지, 조건(출생 시각 미상, 직전 대화) |
| `premise` | 예시에만 해당하는 전제. 줄마다 종류(예시 속 사용자가 말한 사실, 예시용 판단, 판단의 조건, 반대 근거, 예시 재료의 행동 제안, 판단하지 않은 것, 대화 상황) |
| `question`, `answer` | 가상의 사용자 질문, 캐릭터의 답 (문단은 빈 줄) |
| `source` | 출처: 사용자 원문(`user-original`), 사용자 참고 문답(`user-reference`), 작성(`authored`, 근거로 삼은 규칙 결론을 `basis`에 적는다) |

예시의 질문과 답은 실제 이용자의 대화가 아니다. 예시의 근거 ID·날짜·직업·관계·과거 행동은 현재 사용자 자료와 섞지 않는다. 예시 ID는 근거 ref가 아니어서 결과의 refs에 넣으면 검사에 걸린다. 예시 문장에는 근거 ref처럼 보이는 글자(s1, m3 같은)를 넣지 않았다 (테스트가 확인한다).

- 작성 예시(B·C)의 전제는 지금 코드에 있는 규칙 결론의 문장에서 가져왔다 (`first-overview.energy`, `wealth`, `romance`, `family`, `friends`, `place`, `social`, `strengths`, `investment`, `timing`, `career`, `temperament`). 예시를 위해 새 사주 판단을 만들지 않았다.
- 작성 예시의 답에는 행동 숫자(횟수·기간)를 넣지 않았다. 행동의 숫자는 실제 재료에서만 온다. 날짜는 기간 예시 c-01의 예시용 날짜(2027년 4월·7월)뿐이다.
- 진지한 예시(a-07, c-06)는 고통을 놀리지 않는다. 가벼운 선택 고민을 놀리는 예시와 같은 강도로 쓰지 않는다. 진지한 예시는 사용자가 지금 힘들다고 직접 쓴 말이 있을 때만 고른다.
- '허접', '바보', 하트, 웃음소리 같은 표현의 반복으로 성격을 대신하지 않았다. 장난 뒤에는 이유와 행동이 남는다.
- 장문(여러 문단) 예시 7개: a-04, b-01, b-02, b-04, b-08, c-07, c-09. 테스트는 세트마다 8개 이상, 모두 24개 이상, 장문 4개 이상, 목적·주제 범위, B·C가 A의 단어 치환이 아닌지(공백·문장부호를 뺀 16글자 조각 공유 없음)를 확인한다.

| mujin-rw-10 | 10 | 기간 | 1문단 | 4줄 (날짜, 판단, 한계, 활용) |

- 재작성 결과는 원문 답변 그대로다. 질문과 전제도 원문에서 읽는다 (`rewriteView`).
- 중립 초안은 원문 답변에 있는 뜻만 정리했다. 원문 답변에 없는 판단(예: 09 전제의 '모호한 역할 분담')을 초안에 넣으면 Pass 2가 내용을 빼는 법을 배우고, 원문 답변의 뜻을 초안에서 빼면 새 내용을 더하는 법을 배운다. 원문의 건조한 농담과 태도 표현("이름에 ‘자유’가 들어간다고…", "그 빈칸을 자신감으로 메우진 않겠습니다")은 초안에 이미 있는 뜻을 무진의 말로 옮긴 표현이라 초안에는 뜻만 둔다.
- 긴 예시(09)는 줄이지 않았다. 결론·이유·조건·대안·한계를 유지하면서 성격이 드러나는 모습을 보여 준다.
- 초안 문단과 재작성 문단은 번호([1], [2] …)로 짝을 맞춰 보여 준다.

## 4. 선택 정책 `example-select-1.0.0`

| 경로 | 요청 하나에 넣는 수 | 고르는 재료 |
| --- | --- | --- |
| 묘묘 최초 풀이 (reading-3.2.0) | 문답 3개 (긴 예시 하나 이상) | 질문 분야·의도, 비중이 큰 주제(focus·lead), 보통 비중 주제(관련 주제), 기간 질문 여부, 사용자가 쓴 말(질문 요약, 궁금한 점의 사실)로 본 진지함, 출생 시각, 순서 값 = 풀이 ID |
| 묘묘 후속 답변 (followup-3.2.0) | 문답 3개 | 이번 메시지의 질문 분야·의도·반응, 직전 대화 유무, 이번 메시지에서 쓴 말로 본 진지함, 순서 값 = 후속 질문 ID |
| 무진 Pass 2 (mujin-voice-1.1.0) | 재작성 1개 + 문답 1개 | 장의 주제(목차 장 → 주제 표), 처음 궁금한 점에 쓴 사실로 본 진지함, 출생 시각, 순서 값 = 풀이 ID와 장 순번 |
| 무진 후속 답변 (mujin-followup-1.1.0) | 문답 3개 | 질문 분야·의도·반응, 질문과 이어진 장의 주제, 기간 자료 유무, 직전 대화, 순서 값 = 후속 질문 ID |

1. 경로가 맞는 예시만 후보다. 반응 예시는 같은 반응이 담긴 메시지에만, 진지한 예시는 사용자가 지금 힘들다고 직접 썼을 때만, 조건 예시는 그 조건이 있을 때만 후보가 된다. 다른 캐릭터의 카탈로그는 처음부터 받지 않는다.
2. 반드시 채울 자리: 반응이 있으면 그 반응 예시 하나, 진지하면 진지한 예시 하나, 긴 설명이 필요한 최초 풀이는 긴 예시 하나. 무진 Pass 2는 재작성 예시가 긴 설명 자리를 채운다.
3. 남은 자리는 점수로 채운다: 중심 주제(첫 주제 6, 둘째 4, 그다음 2), 관련 주제 2, 공통 예시 1, 질문 의도와 표현 목적의 일치(비교 5, 기간 5, 확정 불가 4, 상황 적용 2), 시각 미상 4, 중간·긴 예시 1. 이미 고른 예시와 첫 주제가 같으면 3을 뺀다. 긴 설명이 필요한 작성에는 짧은 예시를 넣지 않는다. 점수가 0 이하인 후보로는 채우지 않는다.
4. 점수가 비슷한 후보(최고점과 2점 안)끼리는 순서 값으로 하나를 고른다. 무작위가 아니다. 같은 작업(풀이·장·후속 질문)이면 재시도·이어 쓰기·서버 재시작 뒤에도 같은 예시다. 무진 Pass 2는 같은 풀이의 장들이 같은 후보 순서를 보고 장 순번만큼 돌려 고르고, 재작성 예시는 장의 첫 주제가 맞을 때만 그 예시를 고정한다 (같은 예시가 여러 장에 몰리지 않게).
5. 주제가 맞는 예시가 없으면 공통 예시와 남은 후보로 채운다. 예시를 쓰는 버전인데 고른 예시가 0개면(무진 Pass 2는 재작성 예시가 없으면) 조용히 보내지 않고 `examples_unavailable` 오류로 멈춘다.

요청에 더해지는 지시 글자 수 (모델 없이 잰 값, 2026-11-13, 평가 사례): 묘묘 최초 풀이 1,824~2,692자 (3.1.0 지시 10,730자에 더해 약 17~25%), 묘묘 후속 답변 1,757~2,414자, 무진 Pass 2 장마다 1,340~2,547자 (1.0.0 지시 약 4,200자에 더해). 토큰은 실제 호출로만 알 수 있어 재지 않았다 (`docs/LLM_OPERATIONS.md` 조회 SQL로 비교). 길이가 부담되면 정책 버전을 올려 수를 줄인다.

평가 사례 10개의 최초 풀이에서 한 예시가 들어간 사례는 많아야 4개다 (c-07과 b-02가 4개, 테스트는 4개 이하와 서로 다른 예시 12개 이상을 확인한다). 무진 한 풀이의 14장에서 재작성 예시 4개가 모두 쓰이고 한 문답이 다섯 장을 넘지 않는다 (사례 side-job-money에서 가장 많이 쓰인 문답 11번이 4장).

## 5. 지시에 붙이는 모양

예시를 쓰는 버전은 이전 버전 지시 끝에 블록 하나를 더한다. 앞부분은 이전 버전과 글자까지 같고, 입력(사용자 메시지)과 출력 형식(JSON 스키마)은 바꾸지 않는다.

```text
(… 이전 버전 지시 그대로 …)

[캐릭터 문답 예시: 무진 도사]
아래 문답은 [캐릭터]의 관찰, 반응, 설명 전개와 문장 리듬을 보여 주는 가상 예시다. 현재 사용자의 대화 기록이나 판단 자료가 아니다.
- 말하는 방식은 참고하되, 예시의 문장·비유·장면을 그대로 다시 쓰지 않는다.
- 예시의 사용자 사실, 날짜, 수치, 판단, 행동 제안은 현재 입력으로 옮기지 않는다. 예시와 같은 판단이 지금 재료에 없으면 그 판단을 말하지 않는다.
- 현재 답의 사실과 결론은 사용자 메시지로 받은 실제 작성 재료(JSON)만 따른다. 예시의 ID는 근거 ref가 아니므로 refs에 넣지 않는다.
- 예시 답변은 본문 문장의 표현 참고다. 출력의 형식, 칸, 분량은 위 지시와 JSON 형식을 따른다.
- 다시 쓰기 예시(rewrite-example)는 중립 초안이 같은 뜻의 [캐릭터] 설명으로 바뀌는 모습이다. … (Pass 2만)

<rewrite-example id="mujin-rw-09" source="mujin-09">
예시 질문: …
예시 전제 (이 예시에만 해당):
- 예시용 판단: …
중립 초안:
[1] …
다시 쓴 글:
[1] …
지켜야 할 뜻:
- …
</rewrite-example>

<example id="mujin-06">
예시 전제: 따로 없음 (질문에 담긴 말만 다룬 예시)
예시 질문: …
예시 답변:
…
</example>

[캐릭터 문답 예시 끝]
```

넣지 않는 곳: 무진 Pass 1(중립 초안, `mujin-draft-1.0.0`), 질문 정리(`question-1.3.0`, `mujin-question-1.0.0`), 사주 계산, 정적인 입력 안내·버튼 문구, 예시를 쓰지 않던 이전 버전(reading-3.1.0 이하, followup-3.1.0 이하, mujin-voice-1.0.0, mujin-followup-1.0.0)에 고정된 작업. 화면과 PDF에는 예시를 보여 주지 않고, 예시를 사용자 대화로 저장하지 않는다.

## 8. 두 버전 비교하기 (사용자가 직접 실행)

같은 입력에서 예시 미사용(이전 버전)과 사용(현재 버전)의 요청을 모델 없이 파일로 만든다. 비교용 설정은 내보내기에만 있고 운영 기본값(예시 사용)은 그대로다. PowerShell에서는 `--`를 따옴표로 감싼다.

```powershell
# 묘묘 최초 풀이
npm run llm:export '--' --case=job-seeking --date=2026-11-12                          # 예시 사용 (reading-3.2.0)
npm run llm:export '--' --case=job-seeking --date=2026-11-12 --prompt=reading-3.1.0   # 예시 미사용
# 묘묘 후속 답변 (사례의 질문을 후속 질문으로, 반응은 선택)
npm run llm:export '--' --case=job-seeking --date=2026-11-12 --task=followup --reaction=praise
npm run llm:export '--' --case=job-seeking --date=2026-11-12 --task=followup --reaction=praise --prompt=followup-3.1.0
# 무진 Pass 2 (Pass 1은 두 묶음이 같아 한 번만 실행하고, 같은 초안으로 Pass 2를 두 번 만든다)
npm run llm:export '--' --product=mujin-overview --case=side-job-money
npm run llm:export '--' --product=mujin-overview --case=side-job-money --bundle=mujin-1.0.0 --draft=docs/model-comparison/prompts/mujin/2026-11-12_side-job-money
```

플레이그라운드에서 같은 모델·추론 설정으로 두 요청을 실행하고 `npm run llm:render`로 읽는다 (같은 옵션). 보고서 끝의 '예시 문장 겹침' 표는 결과에 카탈로그 예시 답의 16글자 이상 조각이 그대로 나왔는지 보여 준다 (판정 기준이 아니다). 비교할 것:

- 캐릭터가 단순 반말·존댓말 이상으로 드러나는가. 긴 설명(중심 주제, 무진의 중간 장)에서도 성격이 유지되는가.
- 예시 문장·비유·생활 장면이 그대로 또는 비슷하게 늘었는가. 서로 다른 사례에서 같은 답이 반복되는가 (묘묘 `prepare-type`↔`express-type`, 무진 `prepare-first`↔`act-first`).
- 질문에 대한 설명이 짧아지지 않았는가 (말풍선 수·글자 수).
- 사용자 사실이나 날짜가 예시에서 들어오지 않았는가 (예: 2027년 4월·7월, 팀장, 퇴사, 거절, 아픈 가족).
- 조건·반대 근거·행동 제안이 재료와 같게 남았는가 (검사 결과와 무진의 보존 항목).

사람이 읽을 수 있는 조립 결과 예시는 `docs/model-comparison/few-shot-sample/`에 있다 (가상 사례, 개인정보 없음).

## 9. 예시를 고치거나 더할 때

- 사용자가 준 원문(무진 21개, 묘묘 참고 8개)은 고치지 않는다. 바꿀 일이 생기면 원문 ID를 참조하는 별도 예시를 만든다.
- 예시 문장을 고치면 그 예시의 `version`과 카탈로그 버전을 올리고, 새 카탈로그를 쓰는 새 프롬프트 버전을 `PROMPT_EXAMPLES`에 더한다. 이전 카탈로그·버전은 그 버전에 고정된 작업을 위해 남긴다.
- 작성 예시의 전제는 지금 코드에 있는 규칙 결론만 쓴다. 행동 숫자를 답에 넣지 않는다. 근거 ref처럼 보이는 글자를 넣지 않는다.
- 선택 정책을 바꾸면 정책 버전을 올린다. 요청당 수(`EXAMPLE_LIMITS`)를 바꿀 때도 같다.
