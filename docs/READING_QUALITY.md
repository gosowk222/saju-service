# 풀이 품질 고도화 기록 (feat/product-reading-quality)

첫 상품(`first-overview`)의 풀이 깊이, 개인화, 질문 답변 능력을 높인 작업의 진단과 검증 기록이다.

## 1. 진단 (2026-11-10)

가상 입력(1998-09-19 신시, 여성, 서울, "취업 준비 중", 궁금한 점 "언제 취업할까요? 취업보다 창업이 맞을까요?")으로 개선 전 코드의 생성 경로를 실제 모델(`gpt-5.6-luna`)로 한 번 따라갔다.

| 단계 | 개선 전 동작 | 확인 결과 |
| --- | --- | --- |
| 사용자 입력 | 상황과 궁금한 점을 `readings`에 저장 | 정상 저장 |
| 질문 분류 | 없음 | 궁금한 점은 `사용자가 궁금하다고 적은 내용: …` 한 줄로만 LLM에 전달. 주제 순서, 규칙, 재료 선택에 영향 없음 |
| 엔진 재료 | 원국(M01~M04)만 계산 | 기간 재료(대운·세운·월운)를 전혀 계산하지 않음 |
| 선택된 규칙 | 앱 규칙 2개 (가장 큰 십성 계열, 가장 작은 계열) | 주제당 앱 판단 1~2개. 여섯 주제가 모두 같은 재료(가장 큰 계열) 하나에서 나옴. "마감·약속 틀" 보완 문장이 강점·일·돈 세 주제에 그대로 반복 |
| 엔진 기본 결론 | `검토 후보다` 형식의 보류 문장 1개씩 | 기술적인 문장이 그대로 LLM에 전달됨 |
| 계산했지만 쓰지 않은 재료 | 일간 강약, 격국, 용신, 원국 합·충·형, 신살 23개, 12운성, 기둥별 십성(일지 등) | 원국 해석을 풍부하게 만들 재료가 있었지만 계획에 들어가지 않음 |
| LLM 지시 | 말풍선 200자 이내, 핵심 하나, 주제당 2~4개, 전체 약 20개, "단정하거나 겁주지 않는다" | 판단 한 줄을 3~4개 말풍선으로 바꿔 쓰게 됨. 약점은 완곡하게 흐려짐 |
| LLM 원래 응답 | 22개 말풍선, 각 37~85자, 출력 1,383토큰 | **잘리지 않았다.** 재료가 부족해 짧았다 (출력 한도 9,000토큰의 15%) |
| 검사·후처리 | 말풍선 220자 초과, 주제별 개수 범위 이탈, 모든 연도 표기를 오류로 처리 | 긴 설명과 기간 답변을 원천적으로 막는 구조. 이번 사례는 검사에서 삭제된 내용 없음 |
| 저장·화면·PDF | 저장된 메시지 전체를 순서대로 표시 | 일부만 표시되는 문제 없음 |
| 후속 질문 | "저장된 풀이와 근거 안에서만 답한다", 500자 | "언제 취업?"에 "이 풀이만으로 취업 시점이나 합격 여부를 정할 수는 없어요"로 답함. 추가 분석을 시도할 방법 자체가 없었음 |

### 원인 정리

1. 궁금한 점은 저장되지만 판단과 구성에는 쓰이지 않았다. 질문을 나누거나 범위를 판정하는 단계가 없었다.
2. 판단 재료가 너무 적고 모든 주제가 같은 재료에서 나왔다. 엔진이 계산한 다른 재료를 앱 규칙이 읽지 않았다.
3. 프롬프트·캐릭터·검사가 짧고 순화된 문장을 요구했다. 분량 기준이 내용이 아니라 말풍선 수였다.
4. 기간 재료를 요청할 경로가 없어 시기 질문은 항상 "알 수 없다"로 끝났다.
5. 출력 잘림, 파싱 실패, 화면·PDF의 일부 누락은 원인이 아니었다.

엔진은 대운·세운·월운 재료(기간 천간의 십성 계열, 원국과의 합·충·형, 기간 신살, 12운성)를 공개 필드로 제공하지만, 내장 기간 규칙은 "검토할 명리 표지가 있다" 수준의 보류 결론만 낸다. 분야별 기간 해석은 앱 규칙으로 추가해야 하며, 이는 패키지의 의도된 확장 방식이다.

## 2. 바뀐 생성 경로

```text
입력(상황·궁금한 점 원문)
  → [결제 후] 질문 정리: 궁금한 점이 있을 때만 LLM 1회, 구조화 결과를 서버가 검증, 범위는 상품 설정으로 판정 → reading_analyses 저장
  → 엔진 재료: 원국(풀이 기록을 만들 때 계산해 둔 작성 재료) + 시기 질문이 있으면 그 기간의 세운·월운·대운만 계산 → reading_analyses 저장
  → 규칙: 주제별 원국 규칙 6개(주제당 2~4개 판단, 이유·약점·행동 제안 포함) + 기간 규칙
  → 작성 계획: 질문 주제를 앞으로 옮기고 비중을 늘림, 관련 판단을 먼저 꺼냄, 상황별 관점과 생활 맥락 추가, 범위 밖 질문은 넣지 않음
  → LLM 1회 (검사 실패 시 1회 재생성): 시작 → 궁금한 점에 대한 답 → 주제별 설명 → 마무리
  → 검사: 형식, 근거 소속, 질문 누락, 기간 분석 사용, 분석한 달만 날짜 허용, 범위 밖 재유입, 창작 장면의 사실화, 계산값 모순
  → 저장: reading_messages (답변 영역은 topic_id = 'focus'), generation_jobs.generation_meta에 버전
  → 메신저·보관함·PDF: 같은 저장 결과를 읽음
```

## 3. 주제별 판단과 설명 방식

| 주제 | 이전 | 이후 (판단 → 설명에서 쓰는 방식) |
| --- | --- | --- |
| 기본 성향 | 가장 큰 계열 한 문장 | 핵심 특징(1위 계열), 함께 나타나는 이유(1·2위 조합 10종), 상황에 따른 반응(일간 강약), 강점과 약점이 갈리는 조건(강약 × 계열 방향). 약점은 "무엇이·언제·잃는 것·바꿀 점" |
| 강점 | 가장 큰 계열 한 문장 + 보완 문장 | 격국 10종의 능력과 과해졌을 때의 약점, 원국 신살로 본 환경, 가장 약한 계열을 메우는 행동 |
| 일과 직업 | 가장 큰 계열 한 문장 + 같은 보완 문장 | 일하는 방식, 조직형·재량형·균형형, 전문성·협업·독립성의 강약, 취업·창업 조건 비교(같은 기준 4개, 반대 기준을 반대 근거로, 현실 조건은 판단하지 않고 확인 목록으로) |
| 돈 | 가장 큰 계열 한 문장 + 같은 보완 문장 | 수입 유형(만든 것이 돈이 되는 구조·기회형·축적형·돈보다 의미), 유지와 사용, 동업·빌려주기 같은 금전 관계 |
| 연애 | 가장 큰 계열 한 문장 | 매력과 표현(식상 + 도화·홍염), 편안한 관계(일지 십성), 깊어질 때의 약점(일지에 걸린 합·충), 갈등과 조율 |
| 인간관계 | 가장 큰 계열 한 문장 | 협력(비겁·인성·천을귀인), 경쟁과 비교(겁재·양인), 거리와 경계(강약·화개·고신), 갈등 반응(상관·관성·강약) |

같은 재료(예: 비겁 비중)도 주제마다 다른 질문으로 읽는다. 일에서는 재량, 돈에서는 관계로 나가는 돈, 인간관계에서는 경쟁과 비교다. 조건과 문장은 `docs/rules/first-overview.md`에 있다.

설명 방식은 프롬프트 `reading-2.0.0`이 정했고, 말투는 `reading-2.1.0`에서 다시 고쳤다(14절). 핵심 판단 → 이유 → 이 사람의 상황에서 드러나는 모습 → 장점과 약점 → 장면이나 예시 → 행동 제안이 이어지게 하되, 주제마다 시작 방식과 문장 틀을 바꾸고 같은 조언을 여러 주제의 마무리로 반복하지 않게 했다. 말풍선 수는 상한이 아니라 주제별 목표(`depth`)이며, 검사는 화면이 깨지는 길이(2.1.0부터 600자)만 막는다.

## 4. 상황과 궁금한 점의 반영

| 입력 | 반영 위치 |
| --- | --- |
| 상황 선택 | 주제 비중(`focusDomains`), 주제별 관점(`angles`, 예: 취업 준비 × 일 = "지원할 회사와 직무를 고를 때 볼 조건"), 장면을 고르는 생활 맥락(`context`). 상황 이름만 문장에 넣는 방식이 아니다 |
| 궁금한 점 (범위 안) | 답변 영역(질문마다 결론 먼저), 주제 순서(질문 주제가 맨 앞), 비중(focus는 7~9개 목표, 나머지는 standard·light), 먼저 꺼낼 판단(예: 비교 질문이면 취업·창업 비교), 기간 분석, 장면과 조언 |
| 궁금한 점 (범위 밖) | 생성 입력에서 빠짐. 최초 풀이에서 언급하지 않음. 후속 질문이면 한 줄 안내, 차감 없음 |
| 주제는 맞지만 결과 확정 질문 | `answerability: limited`. 알 수 없는 부분을 한 문장으로 말하고 판단 가능한 부분으로 답함 |
| 사용자가 직접 말한 사실 | 범위 안 사실만 "사용자가 직접 알려 준 상황"으로 생성 입력에 넣음 |

한 문장의 여러 질문은 나눠서 받는다 ("언제 취업할까요? 취업보다 창업이 맞을까요?" → 시기 + 비교). 분류는 단어가 아니라 답을 원하는 대상으로 한다 ("데이트 비용 때문에 싸워요"는 연애). 범위는 직전 대화 주제가 아니라 상품 설정으로 판정한다.

## 5. 후속 질문

| 질문 종류 | 처리 |
| --- | --- |
| 기존 풀이 설명 | 질문 주제의 판단(이유·약점 포함)과 그 주제의 이전 말풍선만 보내 구체화 |
| 상황 적용 | 판단 + 새로 알려 준 사실(범위 안만) |
| 시기 | 필요한 기간 재료를 계산(같은 기간은 저장된 것 재사용)해 기간 판단으로 답함 |
| 선택지 비교 | 비교 기준이 있는 판단을 먼저 꺼내 같은 기준으로 비교 |
| 범위 밖 | 질문 정리 1회 뒤 범위 안내, 차감 없음 |
| 여러 질문 | 소질문마다 답하고 사용자가 쓴 순서로 이어 붙임. 차감은 한 번 |
| 판단 불가 | 되묻기(`clarify`), 차감 없음 |
| "그게 무슨 뜻이에요?" | 직전 대화 한 번을 함께 보내 가리키는 대상을 질문 정리 단계에서 풀어 씀 |

저장된 풀이 본문은 덮어쓰지 않는다. 질문 횟수 정책(정상 답변만 한 번 차감, 실패·범위 밖·되묻기 미차감, 같은 요청 재전송과 동시 요청 방지)은 데이터베이스 함수에서 유지한다.

## 6. 계산 재사용과 비용

- 원국은 풀이 기록을 만들 때 한 번 계산해 작성 재료로 저장하고, 생성과 후속 질문은 이 재료를 다시 쓴다.
- 기간 재료는 시기 질문이 있을 때만, 필요한 사주 연도의 세운·월운과 대운만 한 세션에서 계산한다(12개월 기준 약 0.2초). 결과는 `reading_analyses`에 저장해 재시도와 같은 기간의 후속 질문에서 다시 쓴다. 일운은 계산하지 않는다.
- 엔진의 기간 계산은 내부에서 원국 기초 계산을 함께 한다(세션은 요청 하나에서만 유지하는 것이 패키지 정책). 그래서 새 기간이 필요한 요청에서는 그 세션 안에서 원국 기초 계산이 한 번 일어난다.
- 궁금한 점이 비어 있으면 질문 정리 LLM을 부르지 않는다. 말풍선마다 호출하지 않는다. 고전 자료와 대화 전체를 보내지 않는다.
- 검사 실패 재생성은 1회, 네트워크 재시도는 남은 시간 예산 안에서만 한다.

## 7. 저장·화면·PDF 호환

| 항목 | 확인 |
| --- | --- |
| 이전 풀이 (계획 1.0.0) | 메시지 형식은 그대로라 메신저·보관함·PDF가 같은 코드로 읽는다 (단위 테스트: 이전 형식 메시지 PDF) |
| 이전 계획으로 아직 생성되지 않은 풀이 | 작업을 시작할 때 계획 버전에 맞는 `reading-1.0.0` 프롬프트를 고정한다. 이전 형식 검사로 확인한다 |
| 이전 풀이의 후속 질문 | 1.0.0 계획의 주제를 새 질문 처리 모양으로 바꿔 쓴다. 1.0.0 계획에 들어 있던 궁금한 점 원문은 후속 답변 재료에서 뺀다 |
| 새 풀이 | 답변 영역은 `topic_id = 'focus'`, 화면·PDF 제목은 "궁금한 점에 대한 답" |
| 결제·구매 권한·질문 횟수 | 기존 함수 그대로. 되묻기 상태만 추가 (`tests/unit/db.test.ts`) |
| 새 내부 자료 | `reading_analyses`는 RLS를 켜고 정책을 두지 않아 소유자도 브라우저로 읽을 수 없다 (`tests/unit/db.test.ts`) |
| 긴 풀이 | 모바일 줄바꿈, 가로 스크롤 없음, 읽는 위치를 끌어내리지 않는 스크롤, 생성 대기·실패·재시도·재접속은 브라우저 테스트 32개로 확인 |

## 8. 여섯 주제 검증표

자동 테스트는 동작과 실패 조건을 확인한다. 문장 품질은 `gpt-5.6-luna`로 가상 사례 8개를 실제 생성해 사람이 읽고 확인했다 (`docs/model-comparison/2026-11-10-gpt-5.6-luna.md`, 사례 ID는 아래 표의 괄호). 형식 검사 통과를 품질의 증거로 쓰지 않았다.

## 12. 남은 한계

- 규칙 2.0.0은 AI가 작성한 초안이다(`unreviewed`). 출시 전 명리 전문가가 조건과 문장을 검토해야 한다. 특히 연애 기간 판단의 성별 기준 인연 표지와 신살의 생활 해석은 관법에 따라 이견이 있다.
- 질문 분류는 LLM 판단이라 틀릴 수 있다. 실제 확인에서 "쉽게 지쳐요"를 건강으로, "강점을 공부에 쓰는 법"을 시험 결과로 분류한 것을 발견해 분야 설명과 지시를 고쳤다. 같은 종류의 오분류가 다른 표현에서 다시 나올 수 있으므로 운영 로그의 `followups.analysis`(분야·범위)를 주기적으로 확인한다.
- 분류기가 하나의 질문을 비슷한 두 분야로 나누는 경우가 남아 있다 (예: "강점을 회사에서 인정받는 법"을 강점과 일 두 질문으로). 답은 두 관점으로 이어져 반복으로 읽히지는 않았고 차감은 한 번이지만, 같은 내용이 겹칠 수 있다.
- 후속 답변이 "1~3년 후 독립을 넓히는 방식"처럼 기간 분석에 없는 계획 시점을 조언으로 말한 경우가 있었다. 운세 예측은 아니지만 근거가 없는 기간이므로, 다음 프롬프트 버전에서 막을 후보다.
- 범위 밖 재유입 검사는 범위 밖 질문의 정리 문장과 건강·투자·시험 단어만 본다. 의미가 같은 다른 표현까지 잡지는 못한다. 범위 밖 원문은 애초에 생성 입력에 넣지 않는 것이 1차 방어다.
- 기간 판단은 세운·월운 천간의 십성 계열, 기간 신살, 일지와의 관계만 본다. 지지의 십성, 대운과 세운의 상호작용, 용신과의 관계를 분야별로 종합하는 규칙은 없다. 대운은 보조 맥락으로만 쓴다.
- 날짜는 절기 기준 월 단위까지만 말한다. 일 단위 추천일은 일운 재료와 별도 선정 규칙이 필요해 이번 범위에 넣지 않았다.
- 엔진의 기간 계산은 원국 기초 계산을 세션 안에서 함께 한다. 새 기간이 필요한 요청마다 이 계산이 한 번 일어난다 (결과는 저장해 같은 기간에는 다시 하지 않는다).
- 새 migration은 2026-11-10 실제 Supabase에 적용했다. 적용 전 연결된 로컬 앱에서 생성 실패가 있었고 원인과 조치는 `docs/PROGRESS.md`의 장애 기록에 있다. 실제 카카오·구글 로그인과 토스 결제의 끝까지 확인은 이번 작업에서 따로 기록하지 않았다.
- `gpt-6-luna` 비교는 실행하지 않았다 (LIVE_NOT_RUN). 같은 기준일과 사례로 비교하는 방법은 `docs/LLM_OPERATIONS.md`에 있다.

## 13. 패키지 기능 확인

엔진 소스와 설치된 패키지는 수정하지 않았다. 이번 작업에 필요한 기능은 모두 공개 기능으로 해결했다.

| 필요했던 것 | 공개 기능 | 결과 |
| --- | --- | --- |
| 기간 천간의 십성 | `FeatureFacets.periods[].stemTenGod`, `stemTenGodFamily`, period 근거의 `family:` 태그 | 충분 |
| 기간과 원국 일지의 관계 | relation 근거의 `relation:<종류>`, `day-branch` 태그 | 충분. 일지 외 다른 기둥과의 관계 위치는 태그로 구분되지 않아 일지 관계만 썼다 |
| 기간 범위 | `periods[].range` (UTC, 대운은 `approximate`) | 충분. 달력 월과 절기 월의 대응은 범위 시작일로 정함 |
| 원국 기둥별 십성 | `natalFacts.positions[].stem/branch.tenGod` | 충분 |
| 결론 세부 내용 연결 | 결론 ID 형식에 의존하지 않고 규칙이 요청마다 세부 내용을 따로 기록 | 앱에서 해결 |

공개 기능으로 해결하지 못해 엔진 보완이 필요하다고 확인된 항목은 없다. 다만 기간 관계 근거에 상대 기둥 위치(예: 월지)가 구조화된 태그로 있으면 직업 기간 판단에 월지(사회 자리) 관계를 쓸 수 있다. 이는 필요성 메모이며 재현된 오류가 아니다.

## 14. 말투 개선 (reading-2.1.0, 2026-11-10)

실제 풀이를 읽은 피드백: 장면마다 '예시 장면' 제목이 붙고 '예를 들면'이 반복돼 몰입이 깨진다, 약점이 강점·약점 주제 밖에서는 잘 나오지 않는다, 사람과 채팅하는 느낌이 약하다, 중요한 내용이 눈에 띄지 않는다.

| 증상 | 원인 |
| --- | --- |
| '예시 장면' 제목 | 메신저와 PDF가 창작 장면 말풍선 위에 제목을 붙였다 |
| '예를 들면' 반복 | 캐릭터 2.0.0과 프롬프트가 장면을 "'예를 들면'처럼 예시임이 드러나게 시작"하라고 지시했다 |
| 약점이 흐릿함 | 주제마다 약점을 몇 개 말할지 정하지 않았고 '~할 수 있어요'를 막지 않았다. 비중이 낮은(light) 주제에서 약점이 빠졌다 |
| 보고서 같은 말투 | 말풍선 기준이 260자라 한 말풍선에 서너 문장이 들어갔고, 이어 보내는 말풍선마다 프로필과 이름이 반복됐다. 후속 답변은 긴 말풍선 하나였다 |
| 강조 없음 | 강조 수단이 없었다 |

| 영역 | 변경 |
| --- | --- |
| 화면 | 장면 제목 삭제(옅은 보라 면으로만 구분), 이어 보내는 말풍선은 프로필·이름 생략, 후속 답변은 문단마다 말풍선 하나, 강조 구절은 굵게 |
| PDF | 장면 제목 삭제(왼쪽 선과 들여쓰기로 구분), 강조 구절은 굵은 글꼴, 문단 간격 |
| 캐릭터 여울 2.1.0 | 메신저처럼 짧게 끊어 말하기, 장면은 가정하는 말투로 대화에 녹이고 여는 말을 매번 바꾸기 |
| 프롬프트 `reading-2.1.0` | 대화처럼 쓰기(짧은 반응과 설명을 섞고 가끔 되묻기), 질문 답에서 사용자 쪽 약점 짚기, 주제마다 약점 하나 이상을 단정해서 말하기, '예를 들면'은 전체에서 한 번까지, 'N년 후' 같은 기간 숫자 금지 |
| 출력 형식 `narration-2.1.0` | 말풍선마다 강조 구절(`highlight`)을 받고 저장할 때 서버가 문장에 표시. 모델이 구절을 요약해서 적으면 같은 말풍선에서 가장 비슷한 문장 하나를 굵게 만든다. 답변 영역은 말풍선 세 개에 하나 정도, 주제마다 2개까지, 설명 말풍선에만 |
| 후속 `followup-2.1.0` | 결론 먼저, 짧은 문단 2~4개(화면에서 말풍선 2~4개), 사용자 쪽 약점을 흐리지 않기, 문장 안 강조, 기간 숫자 금지 |
| 상품 2.1.0 | 말풍선 260→180자, 형식 상한 700→600자, 주제별 목표 +1, 질문당 4→6개, 전체 형식 범위 20~90→24~120, 안내 문구 "메시지 약 45개" |
| 검사 | 후속 답변이 근거 목록에 질문 ref(q1)를 넣은 것을 문제로 보지 않는다. 실제 실행에서 이 때문에 두 번 거부되어 후속 답변이 실패했다 |

강조는 처음에 문장 안에 `**…**`를 직접 쓰게 했으나 실제 모델이 33개 말풍선 중 1~4개에만 표시했다. 별도 필드로 바꾸자 28개를 채웠지만 모두 요약 문장이라 문장에서 찾을 수 없었다(적용 0개). 같은 말풍선에서 가장 비슷한 문장을 찾는 규칙과 개수 상한을 더해 최종 13개에 적용됐다.

| 항목 (본문 말풍선 기준) | 2.0.0 (가상 사례 8개) | 2.1.0 romance-crush (최종) | 2.1.0 career-jobseeker* |
| --- | --- | --- | --- |
| '예를 들면' 횟수 | 2~5 | 0 | 0 |
| '~수 있어요' 말풍선 | 8~16 | 5 | 4 |
| 약점 표현 말풍선 (단어로 어림) | 1~8 | 13 | 7 |
| 굵게 보이는 말풍선 | 0 | 13 | 1 |
| 말풍선 / 글자 수 | 23~31 / 2,789~4,053 | 33 / 3,425 | 33 / 3,740 |
| 말풍선 평균 글자 | 112~156 | 104 | 113 |
| 검사 문제 | 0 | 0 | 0 |

\* career-jobseeker는 강조를 필드로 바꾸기 전 실행이다. 기록: `docs/model-comparison/2026-11-10-gpt-5.6-luna-reading-2.1.0*.md`. 이번 확인에 쓴 실제 호출은 29회다 (실패 사례 4, 연애 사례 8, 직업 사례 재실행 7, 강조 필드 확인 6, 강조 진단 2 + 2).

남은 점
- 글자 수는 2.0.0과 비슷하다. 말풍선이 짧아지고 개수가 늘었을 뿐 내용 총량은 늘지 않았다. PDF는 후속 질문 2개를 넣어 5~6쪽이다.
- 강조할 문장은 서버가 비슷한 정도로 고르므로 핵심이 아닌 문장이 굵어질 수 있다. 화면을 보고 상한(주제마다 2개)을 조정한다.
- 약점 표현 수는 '약점·손해' 같은 단어로 센 어림값이다. 실제로 단정했는지는 본문을 읽어 확인했다.

## 15. 사주아이 비교 후 확장 (상품 3.0.0, 2026-11-10)

실제 사주아이 990원 풀이 4개(8~12쪽)와 비교한 뒤 결정한 확장이다. 사주아이 PDF는 휴대폰 폭 웹페이지를 인쇄한 것이라 한 쪽에 약 600자가 들어가고, 우리 A4 PDF는 약 1,300자가 들어간다. 글의 양은 사주아이가 1.3~1.9배였다.

| 결정 | 구현 |
| --- | --- |
| 행운의 색·숫자·방향 | 엔진의 용신 오행과 전통 대응표(목 동·초록·3·8 / 화 남·빨강·2·7 / 토 가운데·노랑·5·10 / 금 서·흰색·4·9 / 수 북·검정·1·6)로 규칙이 한 결론에만 정한다. 같은 사주면 늘 같은 값이고, 프롬프트는 그 값만 옮기게 한다. 사주아이 풀이 하나에서 숫자(4·9와 1·6)와 방향(서쪽과 동·북쪽)이 엇갈린 문제를 구조로 막는다 |
| 가족, 친구와 인복, 지역 주제 | 주제 9개. 가족은 육친(인성·재성·비겁, 성별에 따른 자녀 계열)과 연주·월주 관계, 친구는 귀인 신살·가장 큰 계열·용신/기신 오행, 지역은 용신 오행과 역마. 같은 설명이 반복되지 않게 천을귀인과 역마는 새 주제에서만 쓴다 |
| 과거를 짐작하는 말투 | 재미 콘텐츠이므로 "~했을 거예요", "~한 적 있죠?"를 주제마다 한 번 정도 허용. 날짜·이름·사고·질병 같은 구체적인 사건은 금지. 가족 규칙의 해석 문장에 짐작 문장을 넣었다 |
| 건강·투자·미래 | 범위 안으로 옮기고 완곡하게 말한다. 건강 질문은 기본 성향(에너지 관리 규칙)으로, 투자 질문은 돈(투자 성향 규칙)으로 답한다. 검사는 단어 대신 결과 단정·진단·매매 지시·수익 보장만 잡는다 |
| 이전 풀이 | 여섯 주제로 만든 풀이에서 새 주제를 물으면 범위 밖으로 돌려 차감하지 않는다 (`limitToTopics`). 저장된 질문 분석 1.0.0도 그대로 읽는다 |
| 실제 API 호출 | 개발 서버·배포 서버(Next) 안에서만. 스크립트와 테스트는 가짜 서버만 부른다 |

| 확인 | 결과 |
| --- | --- |
| 규칙 테스트 (`tests/unit/life-rules.test.ts`) | 15개 통과. 실제 엔진으로 새 주제 세 개가 근거 있는 결론을 내고, 아홉 주제 문장이 겹치지 않음 |
| 실제 모델 품질 | LIVE_NOT_RUN. 사용자가 개발 서버에서 직접 확인한다 |

남은 점
- 새 규칙 8~12는 AI 초안(`unreviewed`)이다. 육친 해석(특히 성별에 따른 자녀 계열)과 오행 대응표의 지역·해외 예시는 관법과 문화에 따라 이견이 있다.
- 주제가 9개라 출력이 길어진다 (예상 메시지 약 55개). 실제 생성 시간과 토큰은 개발 서버 로그로 확인해야 한다.
- 이전 풀이(여섯 주제)는 새 주제를 보여 주지 않는다. 다시 만들지 않는 정책은 그대로다.

## 16. 명리 설명, 알아맞히는 말투, 사주표 사진, 직업 (상품 3.1.0, 2026-11-11)

사용자 요청: 원국과 판단에 기반한 명리 설명을 간단히 소개하고, 맛보기의 사주표와 오행 비율을 메신저에 사진처럼 보여 주고, "~가 약점이에요"처럼 정해진 형식으로 읽는 말투 대신 "○○ 님은 할 일이 있어도 미루고 미루다 부랴부랴 하는 경우 많죠?"처럼 말하고, 직업 내용을 넣는다.

| 요청 | 구현 |
| --- | --- |
| 명리 설명 | 해석마다 엔진 근거를 옮긴 lore(최대 3줄)를 붙인다. 프롬프트는 주제마다 한두 번 "일주의 사화에 고신살이 있어서"처럼 짧게 소개하고 바로 쉬운 말로 풀게 한다. 재료에 없는 원국 글자·신살을 말하면 검사에서 잡아 다시 생성한다 |
| 사주표 사진 | 메신저에서 첫 인사 다음에 사주원국 표와 오행 비율·글자 수를 사진처럼 보여 준다. 저장된 원국 값만 쓰고 저장 메시지와 데이터베이스는 바꾸지 않는다. 이전 풀이에도 보인다 |
| 알아맞히는 말투 | reading-2.3.0·followup-2.3.0·캐릭터 2.3.0. 약점·강점을 항목 이름으로 선언하지 않고 일상의 모습을 그려 알아맞히듯 말한 뒤, 이유·잃는 것·바꿀 점으로 잇는다. 모든 말풍선을 질문으로 끝내지 않는다 |
| 직업 | 규칙 13: 가장 큰 십성 계열의 직업군과 용신 오행의 업종. 근거가 있는 약점과 함께 둔다 |

| 확인 | 결과 |
| --- | --- |
| 규칙·명리 설명·검사 테스트 | 통과 (`tests/unit/lore.test.ts`, `life-rules.test.ts`, `check.test.ts`) |
| 실제 모델 문장 | LIVE_NOT_RUN. 사용자가 개발 서버에서 확인한다 |

남은 점
- 말투는 프롬프트로만 바꾼다. 실제 모델이 "~죠?"를 지나치게 반복하는지, 명리 용어를 너무 많이 쓰는지는 실제 풀이로 확인해야 한다.
- 규칙 13과 명리 설명의 생극 표현은 AI 초안(`unreviewed`)이다. 지지 십성은 본기만 보고 지장간은 설명하지 않는다.
- 명리 설명 재료는 새로 만든 풀이 기록부터 붙는다. 그 전에 만든 풀이 기록은 명리 설명 없이 새 말투로만 생성된다.

## 17. 주제가 완성될 때마다 먼저 보여 주기 (2026-11-11)

사용자 요청: 풀이가 다 만들어질 때까지 약 40초를 기다리면 오래 걸린다고 느낀다. 글자가 실시간으로 나오지는 않더라도 한 주제가 완성되면 말풍선이 보이고, 쓰는 동안에는 입력 중 표시(움직이는 점)를 보여 준다.

| 구현 | 내용 |

## 19. 묘묘의 성격이 본문과 후속 답변에서 사라지는 문제 (persona 1.1.0, reading-2.6.0, followup-2.6.0, 2026-11-11)

사용자 피드백: 상품 기능을 늘린 뒤 만든 풀이(아홉 주제 + 후속 질문 3개, 사용자가 PDF로 공유. 원문은 저장소에 남기지 않는다)에서 묘묘의 성격이 거의 드러나지 않고 밋밋한 반말 상담문이 되었다. 인사 한 줄만 캐릭터였다.

### 첨부 결과에서 읽은 모습 (관찰)

- 인사 한 줄과 본문에서 자신감을 내비친 말 한 번을 빼면, 아홉 주제가 같은 틀이었다: 판단 문장 → "○○이 N%라 / ○주의 △△에 □□살이 있어" → 가정 장면 → 일반적인 행동 제안. 같은 비율 근거가 세 주제 이상에서 되풀이되었다.
- 말버릇과 이모티콘이 풀이 전체에서 한 번도 없었다.
- 후속 답변 3개 모두 첫 문단이 "○○야, …"로 시작하는 결론 문장이었고, 잘 맞힌다는 칭찬이 함께 온 메시지에도 반응이 없었다.
- 돈 주제에 '취업 준비로 불안한 때'를 전제로 한 조언이 나왔다. 사용자는 궁금한 점에 불안을 적지 않았다.

### 추정 (실제 기록 없이 단정하지 않는다)

- 첨부 결과는 반말과 별명 호칭으로 보아 reading-2.5.0으로 만든 것으로 보인다 (그 이전 프롬프트는 '님' 호칭을 가정한다). 확인은 `generation_jobs.prompt_version`으로 한다.
- 본문이 밋밋한 주된 원인은 "설명에서는 장난을 줄인다" 계열의 지시와 주제마다의 할당으로 보인다. 결과의 반복되는 틀과 비율 근거가 할당과 맞아떨어진다. 다만 모델이 어느 지시를 따랐는지는 알 수 없다.
- 말버릇이 한 번도 없는 것은 "넘기면 다시 쓰게 된다"는 경고와 장난을 줄이라는 지시 때문일 수 있다. 검사에 걸려 다시 쓴 결과인지는 `llm_calls`와 `checked_issue_count`로 확인해야 한다 (어떤 검사였는지는 저장되지 않는다).
- 후속 답변 2번째(다른 주제)가 진지했던 것은 직전 대화의 힘들다는 말 때문에 followup-2.5.0의 진지 모드 지시가 적용된 것으로 보인다.
- 칭찬이 함께 온 3번째 메시지에 반응이 없던 것은 (1) 질문 분석이 반응을 `none`으로 분류했거나, (2) 같은 메시지의 속상하다는 말 때문에 진지 모드 지시가 우선했거나, (3) 모델이 칭찬에 쓰인 '적중률'을 따라 써서 확률 표현 검사에 걸린 뒤 다시 쓰며 반응을 뺀 경우일 수 있다. `followups.analysis.reaction`과 `analysis.llmCalls`로 구분할 수 있다.
- 돈 주제의 불안 전제 조언은 상황 맥락의 "불안 관리"를 사용자의 감정으로 읽은 것으로 보인다.

사용자가 확인할 쿼리와 읽는 법은 `docs/personas/myomyo-evaluation.md` 5절에 있다. 에이전트는 운영 데이터와 `.env`를 읽지 않았다.

## 20. 재료를 옮겨 적는 문제 (persona 1.2.0, reading-2.7.0, followup-2.7.0, 2026-11-11)

19절 변경(reading-2.6.0)으로 만든 실제 풀이(사용자 공유, 원문 미보관)도 "밋밋하게 설명한다, 페르소나 예시 문장과 전혀 비슷하지 않다"는 피드백을 받았다. 같은 원국과 같은 상황(취업 준비 중), 같은 종류의 질문(돈이 들어오는 시기)으로 작성 재료를 로컬 엔진에서 다시 만들어(호출 없음) 결과 문장과 비교했다.

### 확인된 원인 (재료와 결과를 대조한 수치)

| 원인 | 확인한 내용 |
| --- | --- |
| 결과가 재료 문장을 옮겨 적은 것이다 | 이전 풀이(2.5.0)와 이번 풀이(2.6.0)에 똑같이 나온 구체적인 조언 19개 가운데 14개가 재료의 `weakness.change`·`action` 칸에 그대로 있었다. 2개는 묘묘 예시 문장에서 왔고, 모델이 새로 만든 것은 3개였다. 프롬프트를 바꿔도 같은 문장이 나온 이유다. 판단 문장도 재료의 "~하기 쉬운 구조예요"가 "~하기 쉬워"로 바뀐 정도였다 |
| 재료가 말할 자리보다 많다 | 결과에 쓸 수 있는 재료 문장(판단·이유·약점 네 칸·행동·근거)이 약 10,000자로 180자 말풍선 56개 분량이었다. 주제별 목표 말풍선은 합쳐 41개다. light 주제는 목표 3~4개에 재료가 6~7개 분량이었다 (가족 3 대 7, 연애 4 대 7). 재료를 다 담으려면 말풍선마다 해석 두세 개를 몰아넣어야 했다 |
| 같은 재료가 반복해서 들어갔다 | 같은 명리 근거 한 줄이 입력에 15번, 같은 이유("비겁 n%")가 7번 들어갔다. 주의사항은 76줄 가운데 서로 다른 것이 10줄이었다. 결과에서 같은 비율 근거가 여러 주제에 되풀이되었다 |

| 2.6.0 문구가 의무를 늘렸다 | 2.6.0의 "weakness가 있는 해석은 주제마다 빠뜨리지 않는다"는 2.5.0의 "최소 하나"보다 엄격했다. 이 사주의 약점 해석은 36개 중 26개다 (에이전트의 문구 실수) |

### 추정 (실험하지 않음)

- 최초 풀이의 추론 설정(`reasoning.effort = low`)이 낮아, 많은 제약 아래에서 재료를 자기 말로 바꾸기보다 옮겨 적는 쉬운 길을 택했을 수 있다. 설정을 올리면 비용(추론 토큰은 출력 단가)과 시간이 늘어나므로 바꾸지 않았다. 2.7.0 결과를 본 뒤에도 같으면 비교해 볼 후보다.

| 영역 | 변경 |

### 바꾼 것

| 영역 | 변경 |
| --- | --- |
| 분량 (reading-2.8.0) | focus·lead 주제는 풀이의 중심: 해석마다 장면·이유·잃거나 얻는 것·행동까지 풀고 예시나 장면을 하나 더. standard는 해석마다 핵심과 행동까지. light는 그대로 한두 개. 질문 답(focus)은 결론·이유·시기나 비교·약점·행동까지 충분히. target은 설명 말풍선 수의 목표이고 짧은 반응·전환 말풍선은 따로 더한다. 설명 말풍선은 다시 세네 문장(bubbleChars자 안팎)까지, 반응 말풍선은 짧게. 짧아도 되는 곳은 인사, 마무리, 행운 값 |
| 묘묘다운 순간 (묘묘 1.3.0) | 전달 방식에 '묘묘다운 순간'을 더했다: 잘 짚었으면 으스대기("봐, 맞지?"), 습관을 가볍게 놀리기("으이구"), 조언 끝의 얄미운 한마디("안 하면 내가 다 알아"), 마지못한 다정함. 주제마다 한두 번, 설명 사이에, 종류와 말을 바꿔서. 시범에도 이 순간을 넣었다. 지금 고통을 호소한 부분에서는 놀리지 않는다 |
| 말버릇 안내 | "말버릇과 이모티콘도 묘묘의 일부다. 어울리는 자리에 자연스럽게 섞고, 같은 말을 이어서 쓰지 않고 상한을 넘기지 않는다"로 바꿨다. 상한과 검사는 그대로다 |
| 후속 답변 (followup-2.8.0) | 답마다 묘묘다운 순간, 문단 3~5개, 첫 문단은 짧게·설명 문단은 두세 문장까지 |
| 추론 설정 | 최초 풀이 `reasoning.effort` low → medium (`LLM_SETTINGS.tasks.reading`). 질문 정리와 후속 답변은 low 그대로 |
| 그대로인 것 | 재료와 입력(중복 덜어 내기), 출력 형식(narration-2.2.0, 메모 칸), 정확성 검사, 호출 수, 상품 설정, DB 구조, 환경 변수 |

규칙은 2.7.0에서 바꾼 구절만 바꿔 만든다 (`revise`). 바꿀 구절을 찾지 못하면 앱이 시작할 때 오류를 내, 지시가 조용히 빠지지 않게 했다.

### 비용과 시간 (추정, 실제는 서버 로그로 확인)

| 항목 | 2.7.0 (실측, 사용자 확인) | 2.8.0 (추정) |

| 출력 토큰 (글자와 JSON) | 2,458 | 약 4,000~5,500 (중심 주제와 설명 말풍선이 길어진다) |
| 추론 토큰 (출력 단가로 과금) | low | medium에서 늘어난다. 모델과 입력에 따라 크게 달라 숫자로 추정하지 않는다 |
| 대략 비용 (`gpt-5.6-luna` $0.2/$1.2 기준) | 약 $0.0065 | 추론 토큰이 3,000이면 약 $0.014, 8,000이면 약 $0.02 |

- 추론을 먼저 한 뒤 글자가 나오므로 첫 말풍선이 보이기까지 시간이 늘어난다.
- 생성 요청은 280초 안에 끝나야 한다. 같은 요청 안의 다시 쓰기는 남은 시간이 요청 제한(200초)보다 클 때만 하므로, 첫 호출이 80초를 넘기면 검사에 걸렸을 때 같은 요청에서 다시 쓰지 않고 실패로 남는다. 이때 화면의 다시 시도 버튼으로 남은 부분부터 이어 쓴다 (추가 차감 없음). medium에서는 이 경우가 늘 수 있다.
- 작업을 시작할 때 추론 설정이 고정되므로 이미 시작한 작업은 low 그대로다.
